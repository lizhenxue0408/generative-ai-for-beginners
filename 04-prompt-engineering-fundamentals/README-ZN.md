[![提示工程基础](./images/04-lesson-banner.png?WT.mc_id=academic-105485-koreyst)](https://youtu.be/GElCu2kUlRs?si=qrXsBvXnCW12epb8)

## 简介

本模块涵盖在生成式 AI 模型中创建有效提示的核心概念与技巧。你写给大语言模型（LLM）的提示方式同样重要。一个精心设计的提示能够带来更高质量的回复。但 “提示（prompt）” 和 “提示工程（prompt engineering）” 这类术语到底是什么意思？我又该如何改进发送给 LLM 的提示“输入”？这些都是我们将在本章及下一章尝试回答的问题。

_生成式 AI_ 能够响应用户请求，创造出新的内容（例如文本、图像、音频、代码等）。它借助 _大语言模型_ 来实现这一点，比如 OpenAI 的 GPT（“生成式预训练 Transformer”）系列，这些模型经过训练，能够使用自然语言和代码。

用户现在可以使用聊天等熟悉的范式与这些模型交互，无需任何专业技术知识或培训。这些模型是 _基于提示_ 的——用户发送一段文本输入（提示），并收到 AI 的回复（补全）。随后他们可以在多轮对话中迭代地“与 AI 聊天”，不断优化自己的提示，直到回复符合预期。

“提示”如今成为生成式 AI 应用的主要 _编程接口_，它告诉模型要做什么，并影响返回回复的质量。“提示工程”是一个快速发展的研究领域，专注于提示的 _设计与优化_，以规模化地交付一致且高质量的回复。

4. 使用 OpenAI 终结点，将所学技巧应用于真实示例。

## 关键术语

- 提示工程（Prompt Engineering）：设计和优化输入以引导 AI 模型产生期望输出的实践。
- 分词（Tokenization）：将文本转换为模型能够理解并处理、称为 token（词元）的更小单元的过程。
- 指令微调 LLM（Instruction-Tuned LLMs）：经过特定指令微调的大语言模型（LLMs），以提升其回复的准确性和相关性。

## 什么是提示工程？

我们在本课开始时将 **提示工程** 定义为这样一个过程：_设计并优化_ 文本输入（提示），以针对给定的应用目标和模型，交付一致且高质量的回复（补全）。我们可以将其视为一个两步过程：

- 针对给定模型和目标的 _初始提示设计_
- 迭代地 _优化提示_，以提升回复质量

这必然是一个试错过程，需要用户的直觉与付出才能获得最优结果。那么为什么它如此重要？要回答这个问题，我们首先需要理解三个概念：

- _分词（Tokenization）_ = 模型如何“看见”提示
- _基础 LLM（Base LLMs）_ = 基础模型如何处理提示
- _指令微调 LLM（Instruction-Tuned LLMs）_ = 模型现在如何“看见”任务

### 分词

LLM 将提示视为 _token 序列_，其中不同的模型（或模型的版本）可以用不同方式对同一提示进行分词。由于 LLM 是在 token（而非原始文本）上训练的，提示的分词方式会直接影响所生成回复的质量。

要直观感受分词如何运作，可以尝试如下所示的 [OpenAI Tokenizer](https://platform.openai.com/tokenizer?WT.mc_id=academic-105485-koreyst) 等工具。粘贴你的提示——看看它如何被转换为 token，并注意对空白字符和标点的处理方式。请注意，此示例展示的是较老的 LLM（GPT-3）——因此用较新的模型尝试可能会得到不同结果。

![分词](./images/04-tokenizer-example.png?WT.mc_id=academic-105485-koreyst)

### 概念：基础模型

一旦提示被分词，["基础 LLM"](https://blog.gopenai.com/an-introduction-to-base-and-instruction-tuned-large-language-models-8de102c785a6?WT.mc_id=academic-105485-koreyst)（或基础模型）的主要功能是预测该序列中的下一个 token。由于 LLM 在海量文本数据集上训练，它们对 token 之间的统计关系有良好把握，能够有一定信心地做出预测。注意，它们并不理解提示或 token 中单词的 _含义_；它们只是看到一个可以用下一个预测来“补全”的模式。它们可以持续预测序列，直到被用户干预或某个预先设定的条件终止。

想看看基于提示的补全是怎样运作的？将上面的提示输入 [Microsoft Foundry  playground](https://ai.azure.com?WT.mc_id=academic-105485-koreyst)，使用默认设置。系统被配置为将提示视为信息请求——因此你应该会看到一个满足该上下文的补全。

但如果用户想要看到符合某些标准或任务目标的特定内容呢？这就是 _指令微调_ LLM 发挥作用的地方。

![基础 LLM 聊天补全](./images/04-playground-chat-base.png?WT.mc_id=academic-105485-koreyst)

### 概念：指令微调 LLM

[指令微调 LLM](https://blog.gopenai.com/an-introduction-to-base-and-instruction-tuned-large-language-models-8de102c785a6?WT.mc_id=academic-105485-koreyst) 从基础模型出发，并使用示例或输入/输出对（例如多轮“消息”）对其进行微调，这些示例可包含清晰的指令——而 AI 的回复会尝试遵循该指令。

这使用了诸如基于人类反馈的强化学习（RLHF）等技术，能够训练模型 _遵循指令_ 并 _从反馈中学习_，从而生成更适合实际应用、更贴合用户目标的回复。

> _为你提供的内容进行总结，面向二年级学生。将结果控制在一个段落、3-5 个要点内。_

看看结果现在是如何被调整为符合期望的目标和格式的？教育者现在可以直接将此回复用于该课程的幻灯片中。

## 为什么我们需要提示工程？

既然我们已经了解了 LLM 如何处理提示，接下来谈谈 _为什么_ 我们需要提示工程。答案在于一个事实：当前的 LLM 带来了一些挑战，使得 _可靠且一致的补全_ 在不为提示构建和优化付出努力的情况下更难实现。例如：

1. **模型回复是随机的（stochastic）。** _相同的提示_ 很可能用不同的模型或模型版本产生不同的回复。而且即使使用 _同一模型_，在不同时间也可能产生不同结果。_提示工程技巧可以通过提供更好的护栏，帮助我们最小化这些变化_。

1. **模型可能编造回复。** 模型的预训练数据集 _庞大但有限_，这意味着它们缺乏该训练范围之外概念的知识。因此，它们可能生成不准确、虚构，或直接与已知事实相矛盾的补全。_提示工程技巧帮助用户识别并缓解此类编造，例如要求 AI 提供引用或推理过程_。

1. **模型能力各异。** 较新的模型或模型代际将具备更丰富的功能，但也会在成本与复杂度上带来独特的怪癖与权衡。_提示工程可以帮助我们制定最佳实践和稳定可扩展、无缝适配模型特定需求的工作流_。

让我们在 OpenAI 或 Azure OpenAI Playground 中实际操作看看：

- 使用相同的提示搭配不同的 LLM 部署（例如 OpenAI、Azure OpenAI、Hugging Face）——你看到变化了吗？
- 使用相同提示反复搭配 _同一个_ LLM 部署（例如 Azure OpenAI playground）——这些差异有什么不同？

### 编造示例

在本课程中，我们使用术语 **“编造（fabrication）”** 来指代 LLM 有时由于训练局限或其他约束而生成事实性错误信息的这种现象。你可能也在热门文章或研究论文中听过它被称为 _“幻觉（hallucinations）”_。但我们强烈建议使用 _“编造”_ 一词，这样我们就不会通过将类人特征归因于机器驱动的结果而不经意地将这种行为拟人化。这也从术语角度强化了 [负责任 AI 指南](https://www.microsoft.com/ai/responsible-ai?WT.mc_id=academic-105485-koreyst)，去除了在某些语境中可能被视为冒犯或不具包容性的词汇。

想了解一下编造是如何发生的？想一个指示 AI 为某个不存在的主题生成内容的提示（以确保它在训练数据集中找不到）。例如——我试了这样一个提示：

> **提示：** 生成一份关于 2076 年火星战争的教案。

网络搜索向我展示了一些关于火星战争的虚构描述（例如电视剧或书籍）——但没有 2076 年的。常识也告诉我们，2076 年 _在未来_，因此不可能与真实事件相关。

那么当我们用不同的 LLM 提供商运行这个提示时会发生什么？

> **回复 1**：OpenAI Playground（GPT-35）

![回复 1](./images/04-fabrication-oai.png?WT.mc_id=academic-105485-koreyst)

> **回复 2**：Azure OpenAI Playground（GPT-35）

![回复 2](./images/04-fabrication-aoai.png?WT.mc_id=academic-105485-koreyst)

> **回复 3**：Hugging Face Chat Playground（LLama-2）

正如预期，每个模型（或模型版本）都因随机行为和模型能力差异而产生了略微不同的回复。例如，一个模型面向八年级受众，而另一个假设是高中生。但三个模型都生成了可能让不知情用户信以为真的回复，以为事件是真实的。

像 _元提示（metaprompting）_ 和 _温度（temperature）配置_ 这样的提示工程技巧，可以在一定程度上减少模型编造。新的提示工程 _架构_ 也将新工具和技术无缝融入提示流程，以缓解或减少其中的一些影响。

## 提示构建

我们已经了解了为什么提示工程很重要——现在让我们理解提示是如何 _构建_ 的，以便我们评估不同的技巧，进行更有效的提示设计。

### 基础提示

让我们从基础提示开始：一段发送给模型的文本输入，不带任何其他上下文。下面是一个示例——当我们将美国国歌的前几个词发送给 OpenAI [补全 API](https://platform.openai.com/docs/api-reference/completions?WT.mc_id=academic-105485-koreyst) 时，它立即 _补全_ 了接下来的几行回复，展示了基本的预测行为。

| 提示（输入）        | 补全（输出）                                                                                                                     |
| :------------------ | :------------------------------------------------------------------------------------------------------------------------------- |
| Oh say can you see   | 听起来你是在开始唱“星条旗之歌”（The Star-Spangled Banner），即美国国歌。完整的歌词是 ...                                        |

### 复杂提示

现在让我们为那个基础提示添加上下文和指令。[Chat Completion API](https://learn.microsoft.com/azure/ai-foundry/openai/how-to/chatgpt?WT.mc_id=academic-105485-koreyst) 让我们可以将一个复杂提示构建为一组 _消息（messages）_，包括：

- 反映 _用户_ 输入和 _助手_ 回复的输入/输出对。
- 设置助手行为或个性上下文的 _系统消息（system message）_。

请求现在采用如下形式，其中 _分词_ 有效地从上下文和对话中捕获相关信息。现在，更改系统上下文对补全质量的影响，可以与所提供的用户输入一样大。

```python
response = client.responses.create(
    model="gpt-5-mini",
    input=[
        {"role": "system", "content": "You are a helpful assistant."},
        {"role": "user", "content": "Who won the world series in 2020?"},
        {"role": "assistant", "content": "The Los Angeles Dodgers won the World Series in 2020."},
        {"role": "user", "content": "Where was it played?"}
    ]
)
```

### 指令提示

在上面的示例中，用户提示是一个简单的文本查询，可被解读为信息请求。借助 _指令_ 提示，我们可以利用该文本更详细地指定一项任务，为 AI 提供更好的指引。下面是一个示例：

| 提示（输入）                                                                                                                                                                                                                         | 补全（输出）                                                                                                         | 指令类型            |
| :----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | :------------------------------------------------------------------------------------------------------------------- | :------------------ |
| 写一段关于内战的描述                                                                                                                                                                                                                 | _返回了一个简单的段落_                                                                                               | 简单                |
| 写一段关于内战的描述。提供关键日期和事件，并描述其意义。                                                                                                                                                                             | _返回了一个段落，后跟一份带描述的关键事件日期列表_                                                                   | 复杂                |
| 用 1 个段落写一段关于内战的描述。提供 3 个要点，包含关键日期及其意义。再提供 3 个要点，包含关键历史人物及其贡献。将输出以 JSON 文件形式返回。                                                                                       | _在文本框中返回了更详尽的细节，格式化为 JSON，你可以复制粘贴到文件中并按需校验_                                       | 复杂、格式化。      |

## 主体内容（Primary Content）

在上面的示例中，提示仍然相当开放，允许 LLM 自行决定其预训练数据集的哪些部分相关。借助 _主体内容_ 设计模式，输入文本被分为两部分：

- 一条指令（动作）
- 相关内容（影响该动作）

下面是一个示例，其中指令是“用 2 句话总结这段内容”。

| 提示（输入）                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                      | 补全（输出）                                                                                                                                                                                                                                                                             |
| :------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | :---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |

### 使用示例

这是一种你使用主体内容向模型“喂入”一些给定指令下期望输出示例，并让它推断期望输出模式的方法。根据所提供示例的数量，我们可以有零样本提示（zero-shot）、单样本提示（one-shot）、少样本提示（few-shot）等。

提示现在由三部分组成：

- 任务描述
- 几个期望输出的示例
- 一个新示例的开头（成为隐式的任务描述）

注意在零样本提示中我们不得不提供显式指令（“翻译成西班牙语”），但在单样本提示示例中它被推断出来了。少样本示例展示了添加更多示例如何让模型在没有额外指令的情况下做出更准确的推断。

### 提示模板

提示模板是一个 _用于提示的预定义配方_，可以根据需要存储和复用，以规模化地驱动更一致的用户体验。在最简单的形式下，它只是一组提示示例，如 [OpenAI 的这个示例](https://cookbook.openai.com/examples/gpt4-1_prompting_guide?WT.mc_id=academic-105485-koreyst)，同时提供交互式提示组件（用户和系统消息）以及 API 驱动请求格式——以支持复用。

在更复杂的形式中，如 [LangChain 的这个示例](https://python.langchain.com/docs/concepts/prompt_templates/?WT.mc_id=academic-105485-koreyst)，它包含可以用来自各种来源（用户输入、系统上下文、外部数据源等）的数据替换的 _占位符_，从而动态生成提示。这让我们能够创建可复用的提示库，以 **编程方式** 规模化地驱动一致的用户体验。

最后，模板的真正价值在于能够针对垂直应用领域创建和发布 _提示库_——其中的提示模板现已 _优化_ 为反映特定于应用的上下文或示例，使回复对目标用户群体更具相关性和准确性。[Prompts For Edu](https://github.com/microsoft/prompts-for-edu?WT.mc_id=academic-105485-koreyst) 仓库是这种方法的一个绝佳示例，它策划了一个面向教育领域的提示库，重点放在教案规划、课程设计、学生辅导等关键目标上。

## 辅助内容（Supporting Content）

如果我们将提示构建视为包含一条指令（任务）和一个目标（主体内容），那么 _辅助内容_ 就像是我们提供的额外上下文，用于以某种方式 **影响输出**。它可以是调优参数、格式说明、主题分类法等，能帮助模型 _量身定制_ 其回复，以符合期望的用户目标或预期。

例如：给定一个课程目录，其中包含课程体系中所有可用课程的大量元数据（名称、描述、级别、元数据标签、授课教师等）：

- 我们可以定义一条指令：“总结 2023 年秋季的课程目录”
- 我们可以用主体内容提供几个期望输出的示例
- 我们可以用辅助内容标识出最相关的 5 个“标签”

现在，模型可以用少数示例所示格式提供总结——但如果某个结果有多个标签，它可以优先考虑辅助内容中标识的 5 个标签。

## 提示工程最佳实践

既然我们了解了提示是如何被 _构建_ 的，就可以开始思考如何 _设计_ 它们以反映最佳实践。我们可以将其分为两部分来思考——拥有正确的 _心态_，以及应用正确的 _技巧_。

### 提示工程心态

提示工程是一个试错过程，因此请牢记以下三个宽泛的指导因素：

1. **领域理解很重要。** 回复的准确性和相关性是应用或用户所处 _领域_ 的函数。运用你的直觉和领域专业知识来 **进一步定制技巧**。例如，在系统提示中定义 _领域特定的个性_，或在用户提示中使用 _领域特定的模板_。提供反映领域特定上下文的辅助内容，或使用 _领域特定的线索与示例_ 来引导模型走向熟悉的使用模式。

2. **模型理解很重要。** 我们知道模型本质上具有随机性。但模型实现也可能在所用训练数据集（预训练知识）、所提供能力（例如通过 API 或 SDK）以及所优化的内容类型（例如代码 vs. 图像 vs. 文本）方面有所不同。了解你所使用模型的优势与局限，并运用该知识来 _优先安排任务_ 或构建 _针对模型能力优化的定制模板_。

3. **迭代与验证很重要。** 模型在快速发展，提示工程的技巧也是如此。作为领域专家，你可能拥有适用于 _你的_ 特定应用的其他上下文或标准，而这些可能并不适用于更广泛的社区。使用提示工程工具和技巧来“启动”提示构建，然后运用你自己的直觉和领域专业知识迭代并验证结果。记录你的洞察并创建一个 **知识库**（例如提示库），可供他人用作新的基线，以便未来更快地迭代。

## 最佳实践

现在让我们看看 [OpenAI](https://help.openai.com/en/articles/6654000-best-practices-for-prompt-engineering-with-openai-api?WT.mc_id=academic-105485-koreyst) 和 [Azure OpenAI](https://learn.microsoft.com/azure/ai-foundry/openai/concepts/prompt-engineering#best-practices?WT.mc_id=academic-105485-koreyst) 从业者推荐的通用最佳实践。

| 做法                            | 原因                                                                                                                                                                                                                                                |
| :------------------------------ | :------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 评估最新模型。                  | 新一代模型很可能具有改进的功能和质量——但也可能带来更高的成本。评估其影响，然后做出迁移决策。                                                                                                                                                       |
| 分离指令与上下文                | 检查你的模型/提供商是否定义了 _分隔符（delimiters）_，以更清晰地区分指令、主体内容和辅助内容。这可以帮助模型更准确地为 token 分配权重。                                                                                                            |
| 具体且清晰                      | 提供更多关于期望上下文、结果、长度、格式、风格等的细节。这将提升回复的质量和一致性。将“配方”捕获到可复用模板中。                                                                                                                                   |
| 描述详尽，使用示例              | 模型可能对“示范 + 讲解（show and tell）”式的做法反应更好。从 `零样本` 方法开始，只给指令（但不给示例），然后尝试 `少样本` 作为改进，提供几个期望输出的示例。使用类比。                                                                              |
| 使用线索启动补全                | 通过给模型一些它可以作为回复起点的引导性词语或短语，将它推向期望的结果。                                                                                                                                                                         |
| 加倍强调（Double Down）         | 有时你可能需要对模型重复自己。在主体内容前后都给出指令，使用一条指令加一个线索等。迭代并验证，看看什么有效。                                                                                                                                     |
| 顺序很重要（Order Matters）     | 你向模型呈现信息的顺序可能影响输出，即使在学习示例中，这也是由于近因偏差（recency bias）。尝试不同选项，看看什么效果最好。                                                                                                                         |
| 给模型一个“退路（out）”         | 给模型一个 _兜底_ 的补全回复，以便在它因任何原因无法完成任务时提供。这可以降低模型生成虚假或编造回复的可能性。                                                                                                                                     |
|                                |                                                                                                                                                                                                                                                    |

与任何最佳实践一样，请记住 _效果因模型、任务和领域而异_（your mileage may vary）。将这些作为起点，并迭代找出最适合你的方式。随着新模型和工具的出现，持续重新评估你的提示工程流程，重点关注流程的可扩展性和回复质量。
